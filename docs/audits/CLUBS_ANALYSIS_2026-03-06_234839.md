## Direct answer: do we need both unique usernames and display names?

### Recommendation

**Yes.** Keep `display_name` as a separate friendly profile field, and add a new **unique `username`** for Clubs invitations and internal user lookup.

### Why

Verified live and repo facts:
- `public.user_profiles.display_name` **exists** in the live DB.
- `display_name` is used in code:
  - `src/features/auth/services/profileService.ts`
  - `app/(auth)/setup-profile.tsx`
- There is **no live `username` column** on `public.user_profiles`.
- There is **no username UI**, **no username service method**, and **no username-based invite flow** in the repo.
- Authentication is currently **phone OTP based**:
  - `src/features/auth/services/authService.ts` uses `supabase.auth.signInWithOtp()` and `verifyOtp()`.

### Evaluation of possible identifiers for Clubs invites / lookup

- **Phone number**
  - Available through Supabase Auth session, not as a verified public profile identifier in `public.user_profiles`.
  - Poor fit for social lookup and invitations because it is sensitive/private.
  - **Recommendation:** do not use for club invites or user search.

- **`user_id` / auth UUID**
  - Stable internal identifier.
  - Good for backend references, joins, memberships, and invitations after lookup.
  - Not human-friendly.
  - **Recommendation:** keep as the internal canonical identifier only.

- **`display_name`**
  - Already exists and is user-settable.
  - Not guaranteed unique.
  - Unsafe for invite targeting.
  - **Recommendation:** keep for UI only.

- **New unique `username`**
  - Best fit for user search, invite targeting, mentions, and future social flows.
  - Solves ambiguity without exposing phone numbers.
  - **Recommendation:** add this before implementing invite-only Clubs.

- **`referral_code`**
  - Exists in live `public.user_profiles` and repo onboarding flow.
  - Intended for referrals, not social identity.
  - Semantically wrong for Clubs invitations/search.
  - **Recommendation:** do not repurpose.

### Identity recommendation

- **Add unique usernames now** if invite-only Clubs are in scope.
- **Keep display names separate** as the user-facing friendly label.
- Use **username** for invitation lookup and internal club search.
- Use **user_id** as the underlying system identifier after lookup.

If invite-only Clubs are deferred, public and approval-based Clubs can begin before username rollout. Invite-only Clubs should **not** be implemented without unique usernames or another explicit non-sensitive unique identity mechanism.

## Important inconsistencies

### 1. Live DB vs updated product decision on visibility
- Updated product direction: non-members should be able to view all club details.
- Live `book_clubs` SELECT policy `Clubs are viewable based on type` allows non-member detail only for `public` and `approval` clubs.
- **Canonical for now:** live DB behavior is canonical for implementation today.
- **Action needed:** policy update if product now requires public detail for `invite_only` and `author_club`.

### 2. Live role checks vs live policies
- Live `club_members_role_check` allows `member | moderator | admin`.
- But live policies still reference `lead` in:
  - `Applications viewable by applicant and club moderators`
  - `Moderators can update applications`
  - `Moderators can delete messages`
  - `Moderators can create events`
- **Canonical for now:** live DB is canonical, but it is internally inconsistent.
- **Action needed:** policy fix in Supabase.

### 3. Local migrations vs live schema
- `supabase/migrations/20251228114057_003_venues_and_clubs.sql` still reflects an older model with `lead_id` and without clearly matching the live `author_club` / `meeting_type` / `admin_id` shape.
- Live `book_clubs` already has `admin_id`, `meeting_type`, `author_id`, and `author_club` constraints.
- **Canonical for now:** live DB.
- **Action needed:** documentation/backfill reconciliation after explicit review; do not infer from old migration files.

### 4. Local chat migration vs live events model
- `supabase/migrations/20251228114118_004_chat_and_moderation.sql` reflects `club_events.event_type` limited to `online | offline`.

- **Canonical for now:** live DB.

### 5. Older product doc vs current product decision for invite-only visibility
- `docs/architecture/booktalks_mobile_spec.md` describes invite-only clubs as hidden from browse / direct-invite oriented.
- Updated product direction now says non-members can view club details.

### 6. Repo supports `author_club` at type level, but behavior is incomplete
- `src/features/clubs/services/clubsService.ts` includes `author_club` and requires `author_id` in `createClub()`.
- `joinClub()` does not define an author-club join flow.

### 7. Realtime docs vs live deployment

## Recommendation: is a detailed Clubs spec needed before implementation?

### Answer

**Yes — a detailed Clubs specification is required before full Clubs implementation.**

### Why

The deeper audit surfaced verified live issues, not just planning gaps:
- product visibility decision conflicts with live policy
- live role constraints conflict with live policy checks (`admin` vs `lead`)
- local migrations lag behind live canonical schema
- realtime is not enabled for Clubs tables
- invite-only and author-club behaviors are not defined enough to implement safely
- username-based invitations are not currently possible

### What can still start earlier

After policy/source-of-truth alignment, the following can start with relatively low ambiguity:
- route refactor to `app/(tabs)/clubs/...`
- browse screen
- public detail shell
- member-list gating
- public-club direct join
- approval-club application submit flow

Full invite-only, author-club, admin-review, and realtime chat work should wait for the detailed spec.

**Recommendation: approve the visual direction provisionally, but not the complete Library experience or swipe interaction.** The strongest elements are the prominent passage text, persistent book context, and clear primary capture actions. The main weaknesses are ambiguous content ownership, too many concepts during OCR review, and an unproven review-session model.

Before approval, make five decisions:

1. **Separate book text from personal writing.** Saved passages hold excerpts; personal notes hold the reader’s response. Avoid a competing “Quote” note type unless its distinct purpose is demonstrated.
2. **Make capture one predictable task:** select input, prepare a photo only when useful, correct text, confirm page, save, inspect the saved result.
3. **Approve recovery behavior alongside the happy path.** Partial extraction, replacement, unsaved exit, and uncertain saving are essential parts of this task.
4. **Keep optional card reading; defer horizontal swiping.** First test whether session sorting provides value beyond Next/Previous.
5. **Strengthen readability and standardize labels.** The warm palette can remain, but faint metadata, ambiguous icons, and inconsistent terminology need attention.

**1. Recommended structure and content model**

My preferred proposal is:

**Library shelf → Book details → Capture passage → Take photo / Choose photo / Paste text → optional photo preparation → Review and edit → Save passage → Saved passage.**

- Put **Capture passage** directly on book details, near the reader’s saved material. Do not require opening a separate hub before capturing.
- Offer the same action from the per-book saved-material collection.
- Paste text should go directly to text review, with no photo controls.
- Preserve the selected book throughout. Keep page entry on review, where the reader can verify it against the source.
- After saving, show the actual saved record. Back navigation should lead to a useful collection or book context, not invite accidental resubmission.
- Offer an optional personal note after save. Do not require reflection while the reader is merely trying to preserve a passage.

I provisionally support **Notes & passages as a per-book collection**, not necessarily as another mandatory navigation level. A mixed list with explicit record labels and optional type filters could make both kinds discoverable together. Whether this needs a dedicated hub depends on collection size and retrieval testing; the attached back label does not prove that hub exists.

A credible alternative is **a saved-material section directly within book details**, opening into a full collection only when needed. This removes a navigation step and suits small collections, but could overload book details as material grows. Test this against the dedicated hub using both sparse and substantial collections.

For later retrieval, test both “I remember the book/page” and “I remember a phrase.” Per-book browsing addresses the first; Library-wide text search across saved material is a worthwhile proposal if the second is common. It is not evidenced in these images.

Proposed category boundaries:

| Item | Recommended meaning |
|---|---|
| Passage | The book’s words, with book and required page attribution |
| Thought | A personal reaction or reflection |
| Takeaway | A learning expressed in the reader’s own words |
| Action | Something the reader intends to try; no implied task tracking |
| Question | Something the reader wants to explore; no implied answer tracking |
| Quote note | Remove from new-note choices initially; use Passage plus an optional linked note |

**Make note categories optional and changeable later.** Thought and Takeaway overlap naturally; forcing a distinction during capture adds effort without established retrieval value. Keep both only if readers use them meaningfully.

A note may contain quoted text, including OCR inserted from the note editor, but that must remain **one note record** unless the reader explicitly creates a passage. Identify quoted material within the note rather than silently changing record type.

Linking notes to a specific passage would improve provenance, but it is a **product/data-model proposal**, not an established capability. If only book/page association exists, “Add note on this page” is honest; “Add note about this passage” would overpromise. Passage linking also needs rules for replacement and deletion—moderate implementation effort, potentially more with migration.

**3. Should swipe review stay?**

**Not as an approved interaction yet.** Retain optional focused reading, and test whether sorting notes into session outcomes adds meaningful value.

| Option | Benefit | Cost / risk |
|---|---|---|
| Next/Previous reading | Lowest conceptual burden; supports rereading | No explicit second-pass collection |
| Button-led cards | Makes session decisions visible and accessible | Adds a decision to every note |
| Explicit review queue | Readers deliberately choose what deserves another pass | More queue-management interface |
| Horizontal swipes | Potentially quicker for repeated decisions | Hidden mapping, accidental actions, conflict with selection and scrolling |

If a second pass proves useful, test **“Read again this session”** and **“Reviewed this session”** consistently in controls, instructions, and completion feedback. “Set aside” sounds like postponement; “Review again” can suggest an immediate repeat or a future reminder. Combining them does not resolve that ambiguity.

Additional behavior to specify:

- Reviewed means only that the reader chose to move on in this session. It does not complete an Action, answer a Question, or demonstrate recall.
- The set-aside pass starts explicitly; do not cycle notes indefinitely.
- Show position separately from outcome: “Note 2 of 5” is not “2 reviewed.”
- At completion, explain what remains and offer the separate pass or exit. Avoid reward language that encourages rapid dismissal.
- Undo restores the prior card **and** its session decision.
- Opening a long note and returning must preserve card position, scroll context, and session state.
- Vertical scrolling and text selection take precedence over horizontal gestures. Do not commit a swipe while selecting text or using a selection handle.
- Exiting leaves saved notes intact. Make session-progress loss understandable without implying durable recovery.

A short note surrounded by extensive review machinery, as in images 1–2, does not yet demonstrate a reflective benefit. Success should include useful rereading or writing—not just throughput.

**4. Essential recovery and trust states**

These are recommendations for missing behavior, not assertions that it is absent from the implementation.

| State | Required behavior and truthful copy direction |
|---|---|
| Permission denied | Explain which input is unavailable; offer other available inputs. Show settings guidance only when appropriate. Do not repeatedly request permission. |
| No recognized text | “No text was found in this photo.” Offer another image, adjustment, or Paste text. Do not present an empty result as successful capture. |
| Incomplete extraction at the 20,000-character boundary | State that text may be missing. Require an explicit **Continue with partial text** decision; offer retry with a smaller region. Acceptance does not waive passage-length limits. |
| Empty or oversized passage | Show the specific problem beside the editable text. Explain both limits and how much must be removed. Never silently truncate. |
| Missing/invalid page | State “Enter a page number” or the specific invalid value. A disabled Save button alone is insufficient. |
| Same book/page conflict | Show enough existing and incoming text to compare. Offer **Replace passage** and **Keep original**. Explain that replacement has no version history; keep the unsaved incoming text available for correction until the reader leaves. |
| Unsaved exit | Distinguish **Keep editing** from **Discard changes**. Do not promise drafts will survive closing or restarting. |
| Uncertain save | Do not say either “Saved” or definitively “Not saved” without confirmation. Retain the current text while available, check record state, and make retry safe from duplication. |
| Delete | Confirm the specific passage and explain actual consequences for associated notes. Do not imply restore/Undo unless supported. |
| Empty collection / no results | Distinguish “nothing saved yet” from “no matches.” Offer capture/add-note for the former and clear filters for the latter. |
| No notes to review | Explain the scope—such as this book or current filter—and return to saved material. Do not show an inert card stack. |

Two supplied constraints deserve explicit product scrutiny:

- **One passage per page** makes a second useful excerpt compete with the first. Retain explicit replacement now; supporting multiple passages per page would require record-identity, retrieval, and association changes—**M–L effort**.
- **Required numeric pages** exclude some ebooks, unpaginated material, and nonnumeric page labels. Do not invent a page. Broader source-location support is a separate product and validation decision—**M effort or more**, depending on storage assumptions.

**5. Visual, accessibility, and motion principles**

The shared cream surfaces, dark green actions, and literary typography form a plausible Library direction. Image 5 most clearly centers the saved material. However, “calm” currently risks becoming faint, especially in source metadata, helper text, inactive cards, and the apparent Undo control.

From these images, I can assess **relative hierarchy, repetition, visible labeling, crowding, and apparent legibility**. I cannot establish contrast ratios, native font sizes, touch-target dimensions, reading order, accessibility labels, or compliance.

For the next iteration:

- Measure actual text/background tokens. WCAG’s contrast guidance uses at least 4.5:1 for ordinary text and 3:1 for qualifying large text; screenshot appearance alone is insufficient. [W3C](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html?utm_source=chatgpt.com)
- Use a practical Android touch-target goal of approximately 48 dp, including invisible hit areas where appropriate; verify spacing against accidental activation.
- Test narrow layouts, long book titles, the keyboard, and enlarged system text. Image 5’s long back label beside its title is an obvious stress case.
- Allow content to grow and scroll. Do not force long notes into a fixed card or shrink type to preserve the composition.
- Give icons explicit screen-reader names. Announce validation errors, saving outcomes, current card position, and Undo availability.
- Exclude decorative card previews from focus order. After advancing, move focus predictably to the new note, not to an unrelated header control.
- Keep button equivalents for all gestures and an accessible way to use a full photo without precise crop dragging.

Motion should communicate specific state changes:

| Transition | Purpose and stable context |
|---|---|
| Photo preparation → text review | Explain that recognition produced editable text; retain book identity and access to the temporary source while valid |
| Review → saved passage | Confirm persistence, not merely navigation; keep passage and page recognizable |
| Card decision → next card | Show the decision taking effect; keep source and action locations stable |
| Open full note → return | Preserve identity, position, and reading location |
| Undo | Restore the previous card and decision visibly and semantically |

An interrupted swipe should return without changing state until the commit threshold is crossed. A committed action must occur once even if tapped repeatedly. Use an operation-in-progress state for Save and recognition rather than accumulating requests.

Reduced motion should replace card travel, rotation, and stack movement with immediate updates or restrained fades while retaining equivalent feedback. Never delay usable content to finish decorative animation.

Test a working Expo/React Native build on a representative mid-range Android device with long notes, maximum-length input, OCR running, large text, TalkBack, background/foreground transitions, rapid taps, canceled gestures, and reduced motion. Measure response latency and frame consistency; the images cannot establish smoothness.

**8. Five uncoached usability tasks**

Do not teach button names or explain swipe meanings before these tasks.

| Task prompt | Observable success | Failure signals |
|---|---|---|
| **Capture:** “You want to keep this paragraph from page 24 of this book. Start from your Library.” | Finds the book and capture entry, chooses an appropriate input, maintains source context | Hunts in unrelated areas; opens note creation accidentally; assumes photo preparation is mandatory |
| **Correct and save:** “The captured text contains this incorrect word. Keep the corrected paragraph so you can find it later.” | Finds editing, corrects text, confirms page, saves, verifies the saved result | Treats preview as uneditable; misses validation; double-submits; cannot tell whether saving succeeded |
| **Add a note:** “Keep your own reaction alongside this passage without changing the author’s words.” | Creates distinct personal writing and can explain its relationship to the source | Edits the passage instead; creates an accidental duplicate excerpt; gets stuck choosing a category |
| **Retrieve:** “Find the passage about pausing that you saved earlier, and tell me where it came from.” | Locates it from Library and identifies book/page and record type | Depends on recent-screen history; confuses Thought with source text; cannot find attribution |
| **Revisit:** “Read these notes. Leave one to return to during this visit, undo one decision, and open the longest note.” | Understands session scope, finds the deferred note, reverses a decision, returns without losing context | Expects a reminder or completed task; accidentally advances while reading; loses position; cannot start the separate pass |

Run the correction task with controlled variants for partial extraction and same-page conflict. Observe whether readers understand what will be kept and what will be lost without moderator explanation.

**9. Essential changes, later improvements, and next iteration**

**Essential before approval:** clear record boundaries; visibly editable OCR text; correct limits; required-page validation; explicit partial-result and replacement decisions; honest saving/exit behavior; readable metadata; coherent navigation; accessible action alternatives.

**Worthwhile later:** Library-wide saved-text search if retrieval testing supports it; optional category filters; specific passage-note linking; a useful second-pass queue; horizontal swipe shortcuts; restrained transition polish. Durable drafts and multiple passages per page may provide substantial value, but need explicit implementation scope.

**The largest interaction gap: replacement is not one scenario**

The SDD handles replacement of an OCR review reasonably well, but it needs to distinguish:

1. Rescanning a recognized passage.
2. Scanning after the reader has typed a manual note.
3. Scanning while editing an existing saved note.
4. Adding another scan when the reader wants to **append**, not replace.

B04 allows a reader with typed text to switch to scanning. Yet B06/B13/B16 describe replacement recovery primarily as returning to a previous **B07**. That does not fully account for a manual **B05** origin.

Use an explicit return context covering the originating editor, its values, and the pending replacement decision. A canceled scan should restore the appropriate editor—not force a manually written note into an OCR-review screen.

Also decide whether scanning into nonempty text supports **replace only**, **append**, or both. You do not need to add append now, but readers should understand the chosen behavior before their text changes.

**Some screens still carry avoidable complexity**

**Category selection is repeated heavily.** B04 offers five categories and Skip; B05/B07 show the options again. If selection before input is owner-approved, preserve it, but consider a compact selected-category control in the editor rather than repeatedly presenting the whole choice set.

“No category” is an absence of categorization, not a sixth category. The document’s phrase “six category options” is implementable, but risks leaking that model into filters and reader labels. Specify how uncategorized notes appear and whether they can be filtered.

**B13 has too many overlapping recovery actions.** “Try again,” “Back to crop,” another photo, manual writing, and note options are not equally important. If Try again repeats recognition on the same unchanged image, its benefit may be weak. Prefer one primary recovery action, a clear alternative input, and ordinary Back navigation.

**B16’s fallback wording needs qualification.** When the native OCR engine is unavailable, another photo generally does not resolve the problem. Offer manual writing as the usable fallback; show another-image actions only when the failure is plausibly image-specific.

**Crop correctness should be tested independently of recognition accuracy.** “Produces only selected text” is useful end-to-end evidence, but OCR can hallucinate or omit text. Also verify that the actual transformed image contains the expected selected pixels across rotation and orientation cases. That isolates crop bugs from recognition errors.

**The incomplete-text contract is mostly right, but needs a clearer loop**

B14 preserves the important rules: explicit acceptance, no automatic save, and acceptance invalidated after text changes.

The remaining question is what happens when a reader chooses **Keep editing**, edits the text, and then presses Save. The SDD should explicitly state how the warning is reopened or acknowledged from review. Otherwise, readers may encounter a disabled Save with no obvious resolution.

Also carry the **20,000-Unicode-code-point boundary** into this document directly. “Existing safety rules” is too indirect for a contract intended to resolve implementation ambiguity. Keep it clearly separate from the 500-word note limit.

**I would simplify the architecture commitments slightly**

The proposed single transient-session owner is sensible. The document does not need to freeze every component name or insist on a particular decomposition before implementation inspection.

Treat the component list as illustrative. The important boundaries are:

- One owner for draft/session state.
- One validated save lifecycle.
- Reusable note fields.
- Separate capture/crop/recognition responsibilities.
- Explicit reading and recovery states.

Some listed session fields—such as origin, reader origin, current step, replacement snapshot, and dirty baseline—can conflict unless invariants are defined. A transition table showing permitted origins, return destinations, and preserved values would help more than adding further fields.

**Numbering should stay out of this implementation**

The SDD correctly gates it, but “recommended stable saved identifier with atomic allocation” gets ahead of the reader problem.

First establish why readers need Q1/TH1/TK1 identifiers. Are they referencing notes elsewhere, distinguishing similar notes, or navigating a sequence? Existing record IDs already provide technical identity. A user-facing sequence adds allocation and reassignment rules only if it serves an actual reader task.

Keep the decision package, but avoid making numbering infrastructure part of the baseline architecture.

**My approval position**

I would support:

- The notes-first scope **if the owner explicitly chooses it**.
- Read-first saved notes.
- Explicit save destinations.
- Category preservation through OCR.
- Crop-specific recognition.
- A shared form and session lifecycle.
- Building and verifying the manual journey before OCR.

I would hold implementation approval until these are resolved:

1. Scope change and legacy passage access.
2. Roadmap naming and preservation of pending U3.
3. Dirty-exit policy, including capture work.
4. Question and No category persistence.

After that, authorize one manual create → read → edit slice with verified persistence.

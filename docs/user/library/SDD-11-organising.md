## 1. Goal

A reader can put their own labels on books ("Favourites", "Borrowed") and filter the library by them, and can gather notes from any book into named collections ("Lines about grief"), including straight from the swipe section with a double tap.

| Unit | What | Database |
|---|---|---|
| **E** | Labels for books | Migration 1: two tables |
| **F** | Note collections, double tap and collection chips in the swipe section | Migration 2: two tables |

Order: E → F (lead default; the owner may swap them). F needs SDD-10 Unit C on `main`.

## 2. Why

The shelf has only fixed filters (All, Reading, Finished, Wishlist) and notes can only be grouped by book or category. Readers want their own groupings, on their account so they sync across devices.

## 4. Design

### 4.1 Unit E — labels for books

**Behaviour**
- **Suggested labels** (D11-02): Favourites, To re-read, Borrowed, Gift, Signed copy, Classics, in this displayed order. They are constants in the app, not rows; choosing one from Book Details creates and attaches it to that book. An existing label with a server-matching name is offered as that existing label, not a second suggestion. A suggestion becomes available again if that name no longer exists after a rename or delete. The database owns name equivalence; a concurrent entity-name clash remains an error, never silent create success.
- **Limits** (D11-03): up to **25 labels per person** (suggested ones count once used); names 1–24 characters after trimming; names unique per person ignoring case; any number of labels per book.
- **Book Details:** a plain "Labels" row in the existing rows group (`topStyles.rows` in `[bookId].tsx`, with All notes and Book information), after the "Your reading" section — not between the primary action and that section (DP-01: plain secondary row, no fills, no counts in containers). It shows the book's labels as text, or "Add labels" when there are none. Tapping opens a sheet: your labels with ticks (tap to add or remove), unused suggestions, and "New label" (text field, limits shown). At 25 labels, "New label" and unused suggestions are disabled with "You have 25 labels. Delete one to create another."
- **Manage labels:** a "Manage" text button is available in both the Book Details labels sheet and the Home label-filter sheet, including when no books remain. It opens rename and delete. Deleting a label asks for confirmation ("Delete “Borrowed”? It will be removed from 3 books.") and removes it from every book. Existing labels are alphabetical in the picker, Manage and Book Details summary; the alphabetical presentation does not define name uniqueness.
- **Library home filter:** a separate "Labels" button placed directly after the status filter row, **not inside it**: `LibraryFilterBar` is a status radio group (`accessibilityRole="radiogroup"`, `src/components/library/LibraryFilterBar.tsx:23,45`) and is not changed. The button opens a sheet listing your labels; picking one applies the filter and closes the sheet; "Done" closes without changing the selection. The filter is held in memory for the Library visit, survives trips to Book Details, resets on account change, and is not restored after app restart. It filters the shelf/list to books with that label; the button then reads the label's name with a clear (×) button. The label filter **combines** with the status filter (e.g. Reading + Borrowed) — **lead default**. While a label filter is on, the status chip counts are computed over the label-filtered books, so they match what the shelf shows. The button is hidden when you have no labels. With a label filter on and no matching books, the shelf shows "No Borrowed books" (not "Your library is empty") and "Show all books" clears **both** the status and label filters — in the list view, `LibraryEmptyState` and `onShowAll` (`src/components/library/LibraryBookList.tsx:41-47,84`, `index.tsx:192-194`) learn about the label filter. The shelf view has no empty state today (it just shows an empty shelf), so Unit E adds the same message and "Show all books" button below the filter row in shelf view when the filtered set is empty. Deleting the label that is being filtered clears the filter.
- **Shelf order and Arrange:** books inside a label keep the device's saved shelf order. Entering Arrange clears the label filter, exactly as it already resets the status filter to All (`index.tsx:178-180`), so the whole shelf is arranged; while Arrange is on, the Labels button is disabled like the status filter row — **lead default**.
- **Create and attach:** "Add label" creates the custom label and attaches it to the current book. Suggestions use the same recovery rules. A label-only creation from Book Details is not a completed add-to-book action; see §4.3.
- Every save gives visible feedback (`notifySaveSuccess`); failures show an error toast with "Try again" (DP-05). Inline name validation and action-error feedback follow §4.3.
- **One primary per sheet state (DP-03):** the labels sheet's primary is "Done" (also when the 25-label limit is reached); "New label" step: "Add label"; Manage list: "Done"; rename step: "Save name"; delete confirmation: the destructive "Delete".

**Data model (migration 1; applied 2026-10-24, live version `20261024171113`)**
- `public.user_library_labels`: `id uuid pk`, `user_id uuid not null default auth.uid()` (owner, references `auth.users`, on delete cascade), `name text not null`, `created_at`, `updated_at`.
- **Name rule, one definition:** `CHECK (name = btrim(name) AND char_length(name) BETWEEN 1 AND 24)` (24 characters = 24 code points; the app counts the same way with `[...name].length` after trimming) and a **unique expression index** on (`user_id`, `lower(name)`). The database decides what "the same name" means: the app does not compare names itself, and maps any 23505 from creating or renaming a label to "You already have a label called "…"."
- `public.user_book_labels`: `user_id`, `user_book_id`, `label_id`, `created_at`. Primary key (`user_book_id`, `label_id`). **Only the composite foreign keys below** — no single-column `user_book_id` or `label_id` foreign keys — so a PostgREST embed has exactly one path (single plus composite keys to the same table make embeds ambiguous, as on `reading_notes`). This is how the SDD-09 tables are built (live check 2026-10-23: `user_book_reads` and `user_book_progress` have only their composite owner keys).
- **Same owner everywhere:** a row may only link a book and a label that both belong to `user_id`. Enforced with **composite foreign keys** only, the pattern `user_book_reads` uses: `user_library_labels` gets `UNIQUE (id, user_id)`; `user_book_labels (user_book_id, user_id)` references `user_books (id, user_id)` (the existing `user_books_id_owner_key`) and `(label_id, user_id)` references `user_library_labels (id, user_id)`, both on delete cascade and **on update restrict**, matching `reading_notes_book_owner_fkey`.
- **Indexes:** besides the primary key, `user_book_labels (label_id)` (filter by label, label delete) and `(user_id)`.
- **Reading assignments:** page unbounded `user_book_labels` reads used for Home filters and delete counts, with a stable unique order (for example `created_at, user_book_id, label_id`) and the raw response length as the stop condition. A limit of 25 label entities does not limit the number of assignments. Do not display incomplete counts as final.
- **25-label limit:** a BEFORE INSERT trigger takes `pg_advisory_xact_lock(hashtextextended('library-label-cap:' || NEW.user_id::text, 0))` and then counts the user's labels — the repo's cap-lock pattern (`20260822234500_clubs_b02_creation_cap_race_fix.sql:52`). An advisory lock is needed because a row lock locks nothing when the user has no labels yet. The function is `SECURITY DEFINER SET search_path = ''` so the count sees every row of that user regardless of RLS, with `EXECUTE` revoked from `PUBLIC`, `anon` and `authenticated`.
- `user_id` on every new table defaults to `auth.uid()`; the client never sends it.
- **Row guard triggers**, two functions because the tables differ: for **entity tables** (labels, collections), BEFORE INSERT sets `created_at` and `updated_at` from the server clock; BEFORE UPDATE sets `updated_at` and refuses changes to `id`, `user_id` or `created_at`. For **link tables** (`user_book_labels`, `user_note_collection_items`, which have no `id` or `updated_at`), BEFORE INSERT sets `created_at` / `added_at`; there is no UPDATE grant on them, and a BEFORE UPDATE guard refuses any change anyway.
- **RLS** on both tables, `TO authenticated`, written with `(SELECT auth.uid())` (not bare `auth.uid()`, which triggers Supabase's `auth_rls_initplan` advisor): owner-only select, insert (`WITH CHECK (user_id = (SELECT auth.uid()))`), delete; update only on labels.
- **Functions:** every new trigger function is `SET search_path = ''` and has `EXECUTE` revoked from `PUBLIC`, `anon` and `authenticated` (live check 2026-10-23: the project's default privileges grant EXECUTE on new functions to `anon` and `authenticated`). The cap trigger first refuses a missing `user_id` (`IF NEW.user_id IS NULL`) before taking the lock, and raises SQLSTATE `23514` with message `library_label_limit` when the user already has 25; the client maps that to "You have 25 labels…".
- **Migration header:** `SET LOCAL lock_timeout = '5s'`, as in the SDD-09 migration.
- **Grants**, the two-layer pattern of `20261017083830_library_manual_note_privilege_revision_correction.sql:233-256`: `REVOKE ALL` on the table **and** on its columns from `PUBLIC`, `anon` and `authenticated` (Supabase grants new tables to both roles by default), then grant `authenticated` exactly: labels `SELECT`, `INSERT (name)`, `UPDATE (name)`, `DELETE`; link table `SELECT`, `INSERT (user_book_id, label_id)`, `DELETE`. `anon` gets nothing.
- **Client writes:** plain insert/delete/update — **never `upsert`** (column-limited UPDATE grants refuse PostgREST's `ON CONFLICT DO UPDATE`). A duplicate (23505) is treated as success **only for the link table** (`user_book_labels`: the book already has that label). On the labels table it is **not** success: it shows "You already have a label called "Borrowed"." and nothing is saved.
- Migration checked on local Postgres with tests (owner-only access, cross-user link refused, limit race, cascades, grants) before the owner sees the file.

### 4.2 Unit F — note collections

**Behaviour**
- Named groups of **any notes** from any book (D11-05). A note can be in several collections.
- **Limits** (D11-06): up to **25 collections per person**; names 1–40 characters, unique per person ignoring case; no limit on notes per collection.
- **Library home:** a "Collections" text link next to the SDD-10 Home tile (D11-07), hidden during Arrange like the tile. Shown whenever you have any notes **or any collections**, even before the first collection exists and after the last note is deleted. Determine availability from owned notes/collections, independently of a tile-preview fetch failure.
- **Collections screen** (`app/(tabs)/library/collections.tsx`): your collections, newest created first (stable `created_at, id` order), each with its name and "8 notes" as plain text; "New collection"; plain per-row "Rename" and "Delete" text actions. Delete asks for confirmation and removes only the grouping, never the notes. Standalone creation has primary "Create collection" and creates an empty group. At 25, disable "New collection" and the picker creation action with "You have 25 collections. Delete one to create another." Existing membership controls, rename and delete remain usable. The membership picker contains ticks and creation, not an additional Manage menu.
- **States (DP-05)** for both collection screens and both sheets: loading; empty ("No collections yet." with "New collection"; a collection with no notes: "No notes in this collection yet."); error with "Try again"; not found (a deleted collection opened from history: "This collection no longer exists." with "Back to Collections"); offline (cached content shown, every write control disabled with "You're offline."); saving and failed per action (toast). Primaries: collections screen "New collection"; collection screen "Swipe through" when it has notes, none when empty ("Add notes from the note reader or the swipe section." as plain text).
- **A collection's screen** (`collection.tsx?collectionId=…`): its notes, newest added first, a "Swipe through" button, and remove-from-collection per note. Rows are a new library row component that wraps `NotePassageLink` (which takes only a note and has no book title or remove button, `src/components/notes/NotePassageLink.tsx:9-26`) and adds the book title and a "Remove" text button; the shared component is not changed. Data: the collection's item ids (paged, below), then notes and book titles by id with SDD-10's two-query `deckCard` loader and cache.
- **Opening a note** from a collection screen uses the origin `'collection'` (free after SDD-10's rename). `returnFromNote` gains a `collection` branch back to that collection screen, matched by route key like SDD-10's `swipe` branch; `NoteRouteContext` gains `collectionId`. Back labels: reader from a collection "Back to collection"; collection screen "Back to Collections"; collections screen "Back to Library".
- **"Swipe through"** opens `notes-swipe?scope=collection&collectionId=…`: the deck is limited to that collection's notes, title = collection name. Back returns to the collection screen. Preserve the saved Shuffle / Newest first / Oldest first setting; Newest/Oldest use note creation time, whereas the collection's list uses newest-added membership time. Do not introduce a separate collection deck order preference.
- **Note reader:** an "Add to collection" text button in the existing footer alongside Copy, wrapping below it when necessary (the SDD-07 reserved slot).
- **Swipe section** (D11-08, D11-09):
  - **Double tap** on the card opens the collections sheet. To tell a single tap from a double tap, a single tap now waits about 250 ms before opening the full note. Composition: `Gesture.Exclusive(pan, doubleTap, singleTap)` with `doubleTap = Gesture.Tap().numberOfTaps(2).maxDelay(250)` placed **before** `singleTap` (the other order stops double tap from ever firing). JS work from the tap callbacks goes through `runOnJS` / `scheduleOnRN`.
  - **"Add to collection"** secondary button in the button row (fourth button; Next stays the one primary; the row wraps at 200% text). TalkBack uses its own double tap to activate, so retain both the visible button and an Add to collection custom action on the card; card activation still reads the full note. At constrained heights, keep all four controls and chips reachable with a layout that adapts to available height and scrolls where necessary. Scrolling must not compete with the card's vertical gestures. Verify 560 and 640 dp windows at 200% text; no chip-menu redesign is approved by this wording.
  - **Collections sheet:** your collections with a tick next to those holding this note; tap to add or remove; "New collection" at the top (create and add in one step). Confirmation toast ("Added to Lines about grief" / "Removed from Lines about grief") and a short pulse after the sheet closes, only if the same user and affected note are still current (no pulse with reduced motion). Haptic tick on confirmed add; never signal an unconfirmed write as successful.
  - **Collection chips:** after the category chips, one chip per non-empty collection, newest collection first (stable `created_at, id` order). In a book-scoped deck, show only collections containing notes of that book, and keep the filtered deck inside that book; selecting a chip does not broaden scope. Swipe up cycles categories, then collections, then back to All, skipping empty ones. Each remembers its position, as in SDD-10. Chip identity is a tagged value (`{ kind: 'all' }`, `{ kind: 'category', tag }`, `{ kind: 'collection', collectionId }`), so a collection named "Quote" or "All" never clashes with a category. When the swipe section is opened with `scope=collection`, collection chips are not shown (the deck is already one collection).
  - **Sheets** (labels and collections) render `BookFeedbackSlot` inside themselves so their toasts are visible over the Modal, and hide the screen behind from assistive tech (`aria-hidden`, `importantForAccessibility="no-hide-descendants"`, web `inert`) while open.
- Every save gives visible feedback; failures show an error toast with "Try again".
- **One primary per sheet state (DP-03):** the collections sheet's primary is "Done" (also at the 25 limit); "New collection" step: "Create and add"; rename step: "Save name"; delete confirmation: the destructive "Delete". On the collections screen the one primary is "New collection".
- **Changing collections during a visit:** retain SDD-10 successor/end and remembered-position reconciliation. If a selected collection chip becomes empty or is deleted in an all/book deck, fall back to All **within that same scope**. A dedicated `scope=collection` deck stays scoped when emptied (show the collection empty state); when deleted, show "This collection no longer exists." and "Back to Collections". Never silently replace it with all notes.
- **Cache:** creating, renaming or deleting a collection, and adding or removing a note, invalidate the collections keys **and** the SDD-10 deck prefix. Deleting a note and removing a book also invalidate the collections keys (their cascades change counts and contents).

**Data model (migration 2; applied 2026-10-24, live version `20261024171149`)**
- `public.user_note_collections`: `id uuid pk`, `user_id` (owner, on delete cascade), `name text not null` (trimmed, 1–40, check), `created_at`, `updated_at`. Unique on (`user_id`, `lower(name)`).
- `public.user_note_collection_items`: `user_id`, `collection_id`, `note_id`, `added_at`. Primary key (`collection_id`, `note_id`). Only the composite foreign keys below (no single-column ones), for the same embed reason as `user_book_labels`.
- **Same owner:** `user_note_collections` gets `UNIQUE (id, user_id)`; `(collection_id, user_id)` references it. For the note side, a composite foreign key `(note_id, user_id)` → `reading_notes (id, user_id)` uses **the `UNIQUE (id, user_id)` constraint on `reading_notes` added by the applied migration** (`id` was already its primary key, so the extra index changed no data). This was the migration's flagged change to an existing library table. It was added in the same transaction as the new tables; it briefly locks `reading_notes` while the index builds (10 rows at the 2026-10-23 live check). Both composite foreign keys use on delete cascade and on update restrict.
- **Indexes:** besides the primary key, `user_note_collection_items (note_id)` (note delete cascade, deck lookup) and `(user_id)`.
- Name rule (1–40 code points, trimmed, unique expression index on `lower(name)`), 25-collection limit trigger with its own advisory-lock key (`'library-collection-cap:'`), row guard trigger, RLS, two-layer grants (items: `SELECT`, `INSERT (collection_id, note_id)`, `DELETE`), no `upsert` (23505 is success only for the items table; on collections it shows "You already have a collection called …") and local Postgres tests, all as in Unit E.
- **Reading membership:** every read of `user_note_collection_items` (deck chips, counts, a collection's screen) pages like SDD-10's `deckIndex`: ordered by `added_at, note_id` within a collection (also `collection_id` as a tie-break when reading multiple collections), `.range()` per page, stop on the database page length — because a collection has no note limit and PostgREST caps each response at 1,000 rows.
- **Deleting** a note or a book (which deletes its notes) removes the note from every collection through the cascade. Deleting a collection never deletes notes.
- The SDD-10 deck index gains each note's collection ids (one extra owner-filtered query, cached), so collection chips filter in the app like categories.

### 4.3 Rules across both units

- The two migration gates are completed as recorded in the tracker ledger (local filename, md5, live version, effects, readback, advisors). Preserve the applied files. No migration creation/application is part of the app build or this wording update.
- External models never touch Supabase or migration application.
- Never `upsert`. Explicit owner filter on every query, plus RLS.
- SDD-07 DP-01 to DP-07 apply; counts only as plain text (DP-04).
- Shared components are not changed for library looks.

- **Validation and feedback:** trim names and validate code-point length inline ("Enter a label name" / "Enter a collection name"; "Use 24 characters or fewer" / "Use 40 characters or fewer"). Keep failed input. Preserve the specified duplicate/cap messages; use action-specific toasts and "Try again" for read/write failures. Classify database errors by operation and code/message, rather than treating every constraint error as the limit. Avoid duplicate assistive-tech announcements of the same error.
- **Partial or uncertain create-and-attach:** these are two writes, not an atomic operation. Keep a confirmed created entity if attaching fails; identify the partial result and offer an explicit retry of the captured attachment, without creating again or deleting the entity as compensation. After a lost reply, refresh owned state. A matching name proves an entity exists, not that this request created it; identify the uncertain result and let the reader explicitly choose the existing entity for attachment. Retry only the missing attachment once its target ID and desired membership are known. If state cannot be confirmed, retain the uncertainty and input; do not report success or blindly replay creation. Apply this to labels and collections.
- **Concurrent renames:** send the last-read server `updated_at` as a condition on the same owner-and-ID-filtered UPDATE that changes the name; preserve its full server timestamp precision. Request the returned row. If none matches, refresh and distinguish a deleted entity from a changed one, retain the draft, and show a conflict/recovery message rather than overwriting it. A preliminary read followed by an unconditional update is insufficient.
- **Membership changes:** serialize local writes per user and book-label/note-collection pair, with a visible pending state. Send explicit desired add/remove operations, not an inversion of a possibly stale tick. Link-only duplicates/already-absent removals are idempotent success. Membership rows have no version timestamp: do not promise rename-style conflict detection across devices. Reconcile uncertain replies and refresh the server state; concurrent opposite actions on other devices may change the resulting membership.
- **Refresh contract:** fetch on open, focus/foreground return, reconnect and explicit refresh. Continuous polling/Realtime is not required; another device's change can remain unseen on a continuously open screen until a refresh trigger. Preserve cached content on a refresh error and show recovery without calling an unknown result empty. Do not overwrite an unsent name draft when refreshing.
- **Sheet navigation and dismissal:** use substeps inside one Modal. Back/Escape returns a step, or closes at the root; backdrop requests dismissal. Confirm before any transition abandons unsent name changes. Submitted payloads are captured and may finish after dismissal; dismissal does not cancel or roll back an already-sent write. Fence dispatch, retries, cache keys and late feedback to the original user and target; never affect a different account or newly selected note/book. Restore focus to the relevant visible trigger when closing.

## 10. Risks

- **Shared database:** a mistake affects clubs and marketplace; mitigated by local Postgres tests, two approvals and readback.
- **Device-only shelf order vs synced labels:** order differs between devices while labels match; accepted.
- **Single-tap delay:** opening the full note becomes ~250 ms slower once double tap exists.
- **Limit races:** solved by the locking trigger, tested.
- **Naming clash:** the old `'collection'` origin is renamed in SDD-10 Unit C; Unit F must not start before that is on `main`.

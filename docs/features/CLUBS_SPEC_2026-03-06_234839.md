## Product decisions adopted in this spec

1. **Display name and username are separate fields.**
   - `display_name` remains the friendly public label.
   - a new unique `username` is required for invitations and user lookup.
   - `username` will be added to `public.user_profiles`.
   - Clubs identity lookups on mobile use `public.user_profiles`, not a hypothetical `public.users` table.
2. **Non-members can view club details for all club types.**
3. **Non-members cannot view the member list.**
4. **Internal backend relationships use `user_id`; user-facing lookup uses `username`.**
5. **Role model is `member | moderator | admin`.**
   - `lead` is legacy terminology and must be removed from live policies and docs.
6. **Ownership model is explicit.**
   - `book_clubs.admin_id` is the primary owner.
   - v1 does not support additional secondary admins beyond the primary owner record.
   - ownership transfer is out of scope for v1.
   - for `author_club`, the referenced author profile must belong to the same logical user as `book_clubs.admin_id`.

## 1. Canonical domain model

## 1.1 Club types

### `public`
- Publicly discoverable.
- Non-members can open detail.
- Users can join immediately.

### `approval`
- Publicly discoverable.
- Non-members can open detail.
- Users submit join answers.
- Membership becomes active only after moderator/admin approval.

### `invite_only`
- Publicly discoverable at the detail level.
- Non-members can open detail.
- Users cannot self-join.
- Moderators/admins can send invitations by `username`.
- Moderators/admins can manage invitations.

### `author_club`
- Separate `club_type`, not just a tag on another type.
- Requires `author_id` and verified-author status.
- Publicly discoverable.
- Non-members can open detail.
- For v1 implementation, author clubs use an **approval-based join model**:
  - users apply,
  - moderators/admin approve.
- Future expansion can add invite-only author clubs, but that is out of scope for initial delivery.

## 1.2 Role model

### `member`
- View member-only club content.
- Send messages.
- React to messages.
- RSVP to events.
- Vote / nominate if enabled for the club.
- Leave club.

### `moderator`
- All member permissions.
- Review and decide join applications.
- Manage invitations.
- Create/edit/delete club events.
- Delete member messages for moderation purposes.
- Remove members except admins.

Practical current-mobile note: moderators are best treated as a **delegated helper role under admins**. Some broader moderator-management capabilities remain partial or future-facing in the current mobile Clubs scope.

### `admin`
- All moderator permissions.
- Edit club metadata.
- Promote/demote moderators.
- Remove any non-admin member.
- Final owner for club settings and join rules.

Pending applicants and non-members should be treated as **membership states**, not club roles. Store/platform managers remain outside the core club hierarchy.

Delete remains a later lifecycle/governance decision for mobile, not part of the accepted current Manage Club baseline.
Archive is also out of the accepted current Manage Club scope for mobile.

## 1.3 Ownership and admin model

### Canonical owner model
- `book_clubs.admin_id` is the **primary owner** of the club.
- `book_clubs.admin_id` references `auth.users(id)` in the live DB.
- v1 supports **one primary owner only**.
- v1 does **not** support ownership transfer.

### Admin role handling in v1
- The live DB currently allows `club_members.role = 'admin'`.
- For v1 product behavior, the app/server workflows must enforce a **single owner/admin** model.
- Secondary admin memberships are **not** part of the v1 feature set.
- If multi-admin support is desired later, it must be specified separately.

### Author-club ownership rule
- Live `book_clubs.author_id` references `user_profiles(id)`.
- Live `book_clubs.admin_id` references `auth.users(id)`.
- For `author_club`, the selected `author_id` must belong to the profile whose `user_id` equals `book_clubs.admin_id`.
- Because this spans two tables, this rule likely requires an atomic server workflow or DB-side enforcement beyond a simple check constraint.

## 1.4 Invitation lifecycle

### Invitation table status
- Historical note: this was true when the draft spec was written.
- Current reality (`2026-03-07`): `public.club_invitations` now exists live.
- Invite-only flows are therefore only **partially** blocked by backend work now; the remaining live gaps are revoke/read-state workflows, not the base invitation table itself.

### Invitation statuses
- `pending`
- `accepted`
- `revoked`
- `expired`

### Allowed transitions
- `pending -> accepted`
- `pending -> revoked`
- `pending -> expired`

### Invitation permissions
- Moderators and admins can create invitations.
- Moderators and admins are intended to revoke pending invitations, but mobile revoke flows remain backend-dependent until live `revoke_club_invitation` support exists.
- Invitees can accept pending invitations addressed to them.

### Invitation validation rules
- no invitation if invitee is already an active member
- no invitation if invitee has `club_members.status = 'banned'`
- no duplicate `pending` invitation for the same `club_id + invitee_user_id`
- no invitation if the same user already has a `pending` join application for the club

### Acceptance behavior
- Accepting an invitation creates membership immediately.
- It does **not** require an additional approval step.

## 1.5 Application lifecycle

### Live DB baseline
- Live `club_join_applications.status` currently supports only:
  - `pending`
  - `approved`
  - `declined`
- Live table has `UNIQUE (club_id, user_id)`.

### v1 application statuses
- `pending`
- `approved`
- `declined`

### Allowed transitions
- create application -> `pending`
- moderator/admin review -> `approved` or `declined`

### v1 rules
- Applicants cannot edit answers after submission.
- Applicants cannot withdraw applications in v1.
- A declined applicant may reapply only after the previous application record is transitioned or archived by backend workflow.
- Submitted answers are treated as a historical snapshot even if join questions later change.

### DB change note
- If `withdrawn` / `cancelled` or answer-editing behavior is desired, that requires a live DB status/constraint change and workflow changes.

## 1.6 Member status semantics

### Live DB baseline
- Live `club_members.status` currently supports:
  - `active`
  - `muted`
  - `banned`

### `active`
- full access according to role

### `muted`
- can view member-only areas
- can view chat history
- cannot send messages
- cannot react to messages

### `banned`
- cannot access member-only areas
- cannot send messages or react
- cannot accept invitations
- cannot submit new join applications
- remains blocked until an admin/moderator lifts the ban

Historical note: the original draft correctly identified `username` as a required addition, but `username` is now live and already used by the current invite-only manager tooling.

## 3.2 Identity storage source of truth

- Live DB currently exposes `public.user_profiles` as the canonical public identity table used by the mobile app.
- No relevant `public.users` table currently exists in the live public schema.
- `public.user_profiles.user_id` is the canonical auth-linked reference to `auth.users(id)`.
- `username` will be added to `public.user_profiles`, not to a separate mobile-only identity table.

## 3.3 Required identity behavior

### `display_name`
- remains editable and non-unique
- used for rendering UI cards, chat bubbles, and headers

### `username` (required new capability)
- unique across all users
- user-settable with uniqueness validation
- used for:
  - invite lookup
  - invite acceptance flows
  - internal club search/mentions

### `user_id`
- remains the canonical internal foreign key
- invitations resolve `username -> user_id` before insertion

### Not allowed as the invitation identifier
- phone number
- `display_name`
- `referral_code`

## 3.4 Invitation lookup rules

1. User enters a `username`.
2. System resolves that `username` from `public.user_profiles.username` to `user_profiles.user_id`.
3. Invitation row stores inviter `user_id`, invitee `user_id`, club id, status, timestamps.
4. UI renders `display_name` + `username` together.

## 6.3 Public detail data contract

### Why a contract is needed
- The product requires public detail for all club types.
- The raw live `book_clubs` SELECT policy still does **not** expose public-by-type visibility in the way this draft originally wanted.
- Public detail needs safe access to:
  - club metadata
  - current book summary
  - member count
  - limited admin/author summary

### v1 requirement
- Public club detail should be exposed through a **curated public read surface**, not ad hoc raw joins in the mobile client.
- Preferred options:
  1. `public.club_public_details` view with tightly restricted columns, or
  2. a read-only RPC returning the same contract.

### Fields allowed in the public detail contract
- `book_clubs.id`
- `name`
- `description`
- `cover_url`
- `club_type`
- `access_level`
- `meeting_type`
- `member_count`
- current book summary fields needed by the UI
- limited admin/author summary fields needed by the UI

### DB change note
- Historical note: this was true when the draft was written.
- Current reality (`2026-03-07`): `public.club_public_details` exists live and is the current app contract for browse/detail. The app should continue to use the curated contract instead of relying on raw `book_clubs` public reads.
